# be-DailyJob 

> 이 회고는 작업량을 보고하기 위한 문서가 아니라, 
> 오늘 내가 어떤 판단을 했고 어떤 개발 행동을 반복하거나 바꿔야 하는지 확인하기 위한 기록입니다. 
> 각 항목은 길게 쓰기보다, 사실/판단/근거/다음 행동이 드러나게 구체적으로 작성하세요.

### 1. 오늘 완료한 것
- 오늘 실제로 끝낸 기능/수정/학습:
  - ci/cd: 메인 브랜치에 머지한 경우 자동으로 EC2 인스턴스에 배포 파이프 라인 개발
  - 빌드 성공/실패시 이유와 함께 팀 slack에 공유
  - 로컬 개발용 DB 를 h2에서 docker 기반의 mysql로 변경

### 2. 오늘 가장 의미있었던 기술적 판단
- 내가 내린 판단:
  - 로컬 개발용 DB를 h2에서 mysql로 이관.
- 그렇게 판단한 이유:
  - 배포용과 개발용 DB가 달라 실제로 문제가 발생했다.
- 이 판단이 코드 품질/테스트/유지보수에 미친 영향:
  - flyway 데이터 이관에서 엔티티 데이터 타입이 다르게 해석되는 부분을 
  - 이전에는 오류가 발생할 때마다 고쳤어야 했습니다.
  - 정리하자면, 로컬 개발용 DB가 배포용과 달라 deploy 단계에서 실패하는 것을 방지했습니다.

### 3. 가장 막혔던 문제와 해결 과정
- 문제 상황 또는 증상:
  - git runner를 EC2 인스턴스 내부에서 빌드 실패.
- 처음 추측한 원인:
  - EC2 인스턴스 메모리가 1GB 이기에 OOM 을 추측했고 에러 로그 확인 결과 OOM으로 확정.
- 원인을 확인하기 위해 시도한 방법:
  - OOM을 피하기 위해 스왑 메모리를 2GB으로 설정
- 해결 방법:
  - 빌드를 깃허브 서버의 러너에서 빌드 후 .jar 파일만을 서버에 배포하는 방법.
- 다음에 비슷한 문제가 생기면 먼저 확인할 것:
  - 문제를 크게 보는 방법. OOM 이 발생했다고 스왑 메모리를 늘리는 것이 아닌 근본적인
  - 해결책이 필요함.

### 5. 오늘 아쉬웠던 행동(개발과 관련된 것)
- 비효율적이었던 접근/놓치거나 부족했던 점:
  - OOM 발생 시에 상진님께서 빌드를 깃허브에서 하면 된다고 조언함.
  - 그러나, "안될 것 같다"라는 생각만 가지고 스왑 메모리를 늘리려 시도해서 시간을 낭비함.
- 그렇게 된 원인:
  - 이미 내가 작업 중이었기에 팀에서 빌드 과정을 잘 아는 사람이 나라고 착각함.
- 다음에는 다르게 해볼 구체적인 행동:
  - 조언을 들으면 일단 ai에게 질문을 하던해서 그 의견을 검증하라.
